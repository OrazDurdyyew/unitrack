# Журнал архитектурных решений (ADR)

Здесь хранятся решения, которых **нет в ТЗ заказчика** (`docs/spec/requirements.md`). Если решение принято — оно записано здесь; если его здесь нет — оно не принято, и новая сессия не должна считать его само собой разумеющимся.

## Когда писать ADR

- Выбор технологии, библиотеки или зависимости.
- Правило, которому должен следовать весь код (структура, именование, слой, где живёт логика).
- Трактовка неоднозначного места в ТЗ.
- Любое решение, которое другая сессия Claude или разработчик могли бы принять иначе.

Исправления опечаток, локальные детали реализации и всё, что покрыто тестами и очевидно из кода, ADR не требуют.

## Как писать

1. Скопировать `0000-template.md` в `NNNN-короткое-название.md`, где `NNNN` — следующий номер с ведущими нулями.
2. Заполнить все разделы. Раздел «Отклонённые варианты» обязателен: без него через полгода решение пересмотрят заново.
3. Добавить строку в индекс ниже.
4. Закоммитить вместе с кодом, который это решение реализует, или отдельно с префиксом `docs:`.

## Как менять

ADR не редактируются по смыслу. Если решение отменено — пишется новый ADR, а у старого `Статус` меняется на `заменено на NNNN`. Так история решений остаётся читаемой.
