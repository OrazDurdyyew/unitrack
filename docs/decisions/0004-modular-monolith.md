# 0004. Модульный монолит с тремя слоями

Дата: 2026-11-06
Статус: принято

## Контекст

Один сервер, пара сотен активных пользователей, пики утром и вечером. Нет ни нескольких команд, ни нужды масштабировать части независимо. При этом структура должна быть одинаковой во всех модулях, чтобы новая сессия Claude сразу знала, где что лежит.

## Решение

Один сервис. Внутри — модули по предметным областям: `auth`, `users`, `structure`, `students`, `calendar`, `reports`, `changerequests`, `reasons`, `imports`, `analytics`, `notifications`, `audit`, `sync`, `apk`. В каждом модуле три слоя: `handler` (HTTP, права, вызов сервиса), `service` (бизнес-правила, транзакции, аудит), `repo` (запросы через sqlc). Зависимости только вниз. Модули общаются через явные интерфейсы, не лезут в чужие таблицы. Интерфейс появляется, когда есть вторая реализация или нужно подменить в тесте, а не заранее.

## Последствия

- Плюсы: простое развёртывание; единая структура; границы модулей позволят выделить сервис позже, если понадобится.
- Минусы и риски: соблазн «быстро» обратиться к чужой таблице — ловится ревью и линтером зависимостей между пакетами.
- Что сделать: описать структуру модуля в `backend/CLAUDE.md`; проверять импорты между модулями.

## Отклонённые варианты

- **Микросервисы** — сеть между частями, распределённые транзакции, оркестратор; на железе института боль без выигрыша.
- **Полная clean architecture** с портами, адаптерами, DTO на каждом слое — пять файлов на функцию, ничего не даёт при таком размере.
