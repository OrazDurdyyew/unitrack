# 0008. Нативный Kotlin и офлайн-первый подход

Дата: 2026-11-06
Статус: принято

## Контекст

Замдекан отмечает посещаемость на построении и в общежитии, где интернет ненадёжен. Офлайн — штатный режим. Заказчик 2026-11-06 выбрал нативный Kotlin как лучший вариант для офлайна. Приложение раздаётся APK-файлом (см. 0009).

## Решение

Android-приложение на Kotlin: Jetpack Compose, Material 3 с нашими токенами, Room как локальная база, WorkManager для фоновой синхронизации, Hilt, Retrofit с клиентом из OpenAPI, DataStore, minSdk 26. Архитектура MVVM с однонаправленным потоком данных.

Синхронизация: идентификаторы отчётов и строк — UUID с устройства; каждая операция — запись в локальной очереди с собственным UUID (`Idempotency-Key`), сервер хранит обработанные ключи и на повтор отвечает тем же результатом; очередь отправляется строго по порядку; конфликт создания одного отчёта с двух телефонов решает пользователь вручную; расхождение состава группы сервер помечает `unmarked` (см. 0010). Персональные данные (телефоны) на телефоне не хранятся. Refresh-токен живёт 30 дней.

## Последствия

- Плюсы: полный контроль над Room и фоновыми задачами; нет промежуточного слоя между кодом и платформой.
- Минусы и риски: третья среда сборки (JVM/Gradle); синхронизация — самая рискованная часть системы, поэтому тестируется первой.
- Что сделать: Kotlin-клиент из OpenAPI; тесты очереди на Room in-memory до интерфейса.

## Отклонённые варианты

- **Flutter / React Native** — слой абстракции над Room и WorkManager, сложнее отлаживать офлайн.
- **PWA** — ограниченный фон и хранилище на Android, нет надёжной фоновой синхронизации.
